# 性能、动画排查与源码参考

## 当前结论

2026-10-29 的优化基线 `164d02a` 已通过导航、音乐、通话及挂断恢复台架回归。菜单字体由复制到堆内存改为只读映射；实机 manager PSS 从 19,239 KiB 降至 5,763 KiB，私有脏页从 17,932 KiB 降至 1,740 KiB，同组 HiCar 服务总 PSS 从 25,826 KiB 降至 12,072 KiB。统计含映射的已驻留页面，不用文件大小推算内存。

服务启动阶段移除每次强制日志同步，`carlink.service` 自身耗时由 1.233 s 降至 0.463 s；整机启动的两次测量为 23.892 s / 24.024 s，后续应继续分析内核、网络及日志依赖。重复选择正在使用的同一协议保留接收端与代次，五次请求中位数 31.09 ms。HiCar 向 CarPlay 主动切换会显式交接无线资源，跳过先恢复旧 Wi-Fi、随后又拆除的过程；完整连接仍等待手机协商。

HiCar 媒体循环复用轮询数组，单路 PCM 直接移交缓冲，多路仍保留原混音语义。不同画面与音乐状态对 CPU 影响明显，性能比较采用相同协议、相同播放场景的多次采样；只凭语言迁移或不同场景样本不计算加速比例。

### CarPlay 媒体桥接 Rust 迁移

`90ee05a` 将常规 CarPlay 输出改为 `carlink carplay-output`：OXP 帧协议、H.264 转封装、媒体排队、音轨控制、输入回传、麦克风重采样和 Opus 送回均由 Rust 管理；视频保持透传，音频继续复用精简 FFmpeg 与 libopus。参考 Python 实现保留，生产默认路径没有 Python 进程。

实机静态画面、无音频解码子进程的三次五秒采样：

| 指标 | Python 桥接 | Rust 桥接 |
| --- | ---: | ---: |
| 服务总 PSS 中位数 | 21,887 KiB | 14,474 KiB |
| 服务 CPU 中位数（单核 100%） | 19.93% | 21.10% |
| ARMv7 主程序大小 | 1,662,148 B | 1,785,028 B |

此组实测收益为总 PSS 减少约 34%，主程序增加 120 KiB；CPU 未显示改善。后续持续优化应围绕实际热点和唤醒次数，而非继续替换已经运行于原生库中的编解码计算。音乐、页面操作、双向通话及挂断恢复由用户台架回归通过；HiCar ↔ CarPlay 三次真正切换保留同一个 CarLife PID，USB 均保持连接，自动连接用时约 8.88 / 13.64 / 8.97 秒（从切换请求到接收端 ACTIVE）。

2026-10-23 部署源头最高 30 fps 后，用户确认播放/暂停音乐时滑动、点击均流畅，声音连续。随后应用进出仍停约三秒；原始视频录制也显示该停顿，完整重启 iPhone 后动画恢复，减弱动态效果可以关闭。

当前保留 H.264 透传、800×480、最高 30 fps、Opus 语音能力与缓冲音频声明。未验证直接控制 iPhone 目标视频码率的接口，暂不继续盲目降低码率或重定 PCM 时钟。

## 实现

- 仅 headless forward 模式启用 `CARLINK_LOW_LATENCY=1`。上游利用 iPhone screen header 的发送时刻与板上 CLOCK_MONOTONIC 建立最小传输偏移估计，允许小幅时钟漂移，标记延迟到达的视频；流连接另发进程纪元与系统单调时钟的偏移，音频时间线独立对齐。未提供发送时钟的帧退回板上接收时刻。
- 上游发送队列由 128 降至 32 项；发送前跳过超过 120 ms 的旧视频，限频请求关键帧。
- 媒体桥接最多排队四个视频帧、每角色六个音频块；视频/音频排队预算 120 ms，live socket 发送缓冲单独设为 32 KiB。旧视频清除后等待新 IDR，不随机丢弃参考 P 帧后继续发送依赖帧。
- 本地协议新增 kind 6 视频恢复标记；video flags bit 1 表示 CLOCK_MONOTONIC 采集时刻。恢复视频不再发送全局 inactive/active，不重启音频播放对象。
- Rust 读取队列及 USB 写队列均增加时限；视频与音频使用独立代次；过期视频触发 IDR 恢复，过期音频块丢弃。USB 已开始传输的帧保持完整；控制响应不按媒体时限丢弃。
- 协议循环等待由 10 ms 缩短到 2 ms。关键帧请求限频到每 250 ms，并在等待关键帧期间重试。
- 每五秒输出 `forward_latency`、`live_latency`、`usb_tx_latency`：源到转发年龄、本地队列年龄、socket 发送时间、USB 排队和写入时间、丢弃量。仅记录统计，不保存媒体。

这些预算约束各段软件排队，实际画面延迟还包含 iPhone 编码、无线接收和车机解码显示。复测按相同页面切换和音乐操作观察，统计数据与用户看到的结果分别记录。

## 回归检查

- 合成源故意先发送两秒前的 IDR，再发新画面；旧画面泄漏到 CarLife 即失败。
- 上游纯函数检查：手机时间只前进 100 ms、接收时间前进两秒，映射后仍能识别约 1.9 秒额外等待；随后新帧恢复正确时刻。
- 检查源时钟标记跨真实 Python、Rust 会话可用，视频与音频时间戳仍单调。
- 检查视频恢复保留音频状态和音频代次、关键帧请求限频、完整按键脉冲和 Lexus 输入回归。
- 检查过期 USB 媒体丢弃而控制响应保留；完整协议帧边界继续校验。

## 首轮硬件观察及修正

应用 `2636428` 经 CI 成功构建并远程部署。用户反馈画面更流畅，但声音断续。约 70 秒采样记录：

- Python 转发队列的五秒窗口最大值：中位数 19.88 ms，最高 23.15 ms；socket 写入最高 3.96 ms。
- Rust 侧视频年龄的窗口最大值：中位数 58 ms，最高 73 ms。
- USB 队列最高 94.53 ms，单次写入最高 94.51 ms；超时丢弃计数为 0。
- 源端出现最高 556.11 ms 的旧帧；已触发丢弃与关键帧恢复，日志观察到恢复约 68–90 ms。该时延基于发送时钟的最小偏移估计。
- 服务未自动重启。

定位到 Rust 中遗留的音频门控：视频等待关键帧时会丢音频块。修正为音频继续通过，并扩展回归测试，在等待关键帧状态下验证音频数据确实输出。压缩音频解码入口恢复 16 包缓冲并独立设置 500 ms 容忍窗口，适配 AirPlay 突发包；解码后的 PCM/live/USB 仍使用短队列及 120 ms 期限。

协议元数据另经真实上游 `oxp_wire::write` 检查：采用标准 stats 消息，`clockOffsetUs` 按规范编码为十进制字符串。

## 音乐播放时的画面延迟

`95d7147` 修正后，用户先确认声音流畅，随后明确复现：不播放音乐时操作较及时，播放音乐时画面操作约延迟一秒。曾出现短暂卡住并自行恢复。关闭 buffered-audio 声明的对照配置仍有该现象，因此恢复原声明。

临时时钟诊断记录到视频时间戳距当前约 4–49 ms，而 PCM 音频时间戳持续落后约 90–405 ms。压缩音频时间戳取自解码前输入，输出受解码缓冲及 PCM 节奏控制，两个时刻存在差距。

曾尝试在 headless 模式下把 PCM 时间戳锚定到实际输出时刻。用户对照反馈声音连续，但音乐播放期间画面仍有变化的延迟，最高 2 秒以上。该修改已通过 `2c47acc` 撤回，保留原音频时间线。

码率方面，固定上游实现提供帧率、分辨率协商，未发现直接设置视频目标码率的接口。动态画面日志约 60 视频包/秒，约 2–3 Mbit/s。CarLife 声明 30 帧，OXP 消费端偏好也为 30 帧，但上游会话初始帧率默认 60，偏好更新不直接改变已建立会话。

`d021e10` 在 headless 模式建立 AirPlay 会话时，把初始最高帧率限制到 30，保留 800×480 和 H.264 原码流转发。新增五秒窗口内实际视频 AU 帧数和有效载荷字节数统计，分别输出帧率和 Mbit/s，供硬件确认。

## 1. 用户 DiPlay / CarProjection：直接转发与独立发送

### 已有设计

- `DiPlay/shared/.../media/CarLifeVideoBridge.kt`：单独的 `carlife-h264-writer`；队列超过 6 帧或字节预算时清理并请求关键帧；发送前有 250 ms 年龄检查；重复相同编码配置不会反复关闭管道。
- `DiPlay/shared/.../media/VideoDecodeQueue.kt`：接收和解码分离，丢失参考链后等待随机访问帧；`VideoInputPump` 在等待输入缓冲时持续排空解码输出。
- `DiPlay/shared/.../media/AndroidMediaSink.kt`：收到编码帧时直接提交 CarLife bridge；解码音频优先写向 CarLife 路由，headless 转发不要求本地扬声器播放。
- `CarProjection/.../VideoQueueBudget.java`：最多 8 个待发送视频包和 2 MiB；`MsgProcess.java` 对视频来源和 USB 会话分别记录代次。

### 对我们的意义

这些已有实践支持继续走 H.264 透传，不在 H3 上增加视频解码、缩放和重编码。Linux 已实现队列限额与 IDR 恢复，源帧率匹配已部署；隐藏音频缓存测量和显示端观测是后续排查手段。

## 2. DiPlay 上游：两项新的音频修复

- [PR #788：音频时钟漂移](https://github.com/shihabal3amri/DiPlay/pull/788)：维护者根据某车机实际写入样本数与播放头进度，分析出播放时钟约快 0.76%；音乐缓冲逐渐耗尽，周期性重新缓冲。其设计对音乐使用缓冲水位反馈和有限速率微调。
- [PR #814：旧音乐包积压和错误降速](https://github.com/shihabal3amri/DiPlay/pull/814)：把解码前压缩音频队列按 RTP 时间跨度计入积压；对持续过量积压进行恢复，短暂无线突发保留；压缩包积压时暂停学习硬件时钟漂移。作者的确定性测试复现了约 4 秒压缩音频积压，实车效果仍待报告者验证。

适合借鉴的是“同时测量解码前、解码后、设备消费进度”，以及按时间而非包数定义预算。`AudioTrack.setPlaybackRate` 属于 Android 本地播放接口；我们的声音最终由车机播放，移植时需要 CarLife 可用反馈或独立测量，不能直接套用该 API 与控制参数。

当前 `receiver/forward.py::AudioDecoder` 使用压缩包队列、FFmpeg stdin/stdout、PCM 20 ms 节拍。stdout 读取线程同时负责等待播放时刻，等待期间停止读取；缓存可滞留在子进程或管道中，而下游统计仍然很小。需要记录输入样本时间跨度、解码耗时、管道可读字节、输出样本数及节拍落后量。

此前直接重定 PCM 时间戳的实验使用户观察到延迟加重，已回退。新的时钟实验必须先测量多阶段积压，并保留独立回退开关。

## 3. catplay：最相关的原生 Linux 架构参考

[catplay](https://github.com/catplay-labs/catplay) 面向嵌入式无线 CarPlay 盒子；README 列出的一个主要平台也使用 AIC8800D80。其目标板、无线连接方式与本项目仍需分别适配。

重点源码：

- `carplay/catplay_carplay/src/screen/rx/screen_rx_session.rs`：保留帧目标时间与本地到达时间，统计显示时间差、负提前量和晚到帧，再交给 sink。
- `.../clock/media_clock.rs`：明确本地和远端时间域之间的映射；`media_pll.rs` 有相位/频率校正结构，但当前 `DISABLE_PLL=true`。
- `.../audio/api_rx.rs`：音频 source/sink 分离，围绕样本读写和消费进度工作。
- `.../rtp/play/rtp_player.rs` 与 `carplay/catplay_audio`：RTP 处理、进程内解码和 SPSC 环形缓冲。

适合迁移的是进程内音频解码、按样本数计量的有界 PCM 环和分离的时钟观测。保留现有 FFmpeg 解码器库也是一种实现路径，不必为了借鉴架构而整体切换 codec 库。

替换整个接收端还涉及认证接口、蓝牙引导、热点、输入反馈和 ARMv7 构建集成，先在现有 OpenXPlay 上改良数据路径更便于对照。

## 4. HeadSwap：根据实际输出拥塞控制负载

`aa/BitratePolicy.kt` 把 backlog 毫秒数进行平滑，结合实际 drain 速率，拥塞时降低码率，稳定一段时间后逐步提高。当前代码下降参考点 300 ms、上升参考点 100 ms、平滑时间常数 1 秒。

这比只看 Wi-Fi 协商速率或平均 Mbps 更接近瓶颈。我们可以先引入相同的观测量：视频 AU 大小分布、USB write 分布、队列时间跨度、关键帧恢复频率。控制 iPhone 码率的接口需要单独确认：当前 OpenXPlay `AirPlayDisplayConfig` / display plist 暴露分辨率和 maxFPS，没有现成的视频 bitrate 字段。HeadSwap 能直接调 Android 编码器，这部分能力与 H.264 透传不同。

## 5. PlayPort、UxPlay 和社区经验

- [PlayPort](https://github.com/youcci/playport)：DiPlay 协议移植到 JVM 服务端，编码媒体通过 WebSocket 到浏览器，用 WebCodecs 解码并显示 FPS、码率、队列和延迟。适合作为诊断界面参考；其蓝牙引导当前以 macOS 为验证平台，H3 生产链路不需要加入浏览器和额外媒体转发。
- [UxPlay 文档](https://github.com/FDH2/UxPlay/blob/master/README.txt) 和 [RPiPlay #265](https://github.com/FD-/RPiPlay/issues/265)：延迟累积需要区分按时间戳播放与立即显示，以及消费能力落后于输入的情形。普通 AirPlay 的两秒音频模式与 CarPlay 交互不是同一配置，参数不能直接照搬。
- [个人 AirPlay 同步实践](https://gioele.dev/blog/latency-free-airplay-audio-streaming/) 展示了主动缓冲以维持音视频同步的另一种目标，适用于理解缓冲取舍。
- [vivo 智能车载官方社区](https://bbs.vivo.com.cn/newbbs/thread/37036311?show_title=1) 对帧率优先产生卡顿/延迟的车机建议降到 30 帧，支持先做兼容帧率实验。
- [GStreamer queue 文档](https://gstreamer.freedesktop.org/documentation/coreelements/queue.html) 清楚区分线程解耦、时间/字节/数量限额和阻塞行为。应借其有界队列观念；本项目视频链路并未使用 GStreamer。

## 应用过渡动画隔离（2026-10-23 00:35）

用户对照：iPhone 原先关闭“减弱动态效果”；开启后淡入淡出非常流畅，关闭后再次出现应用图标留在原位约三秒、随后直接进入应用。退出时也有类似停顿。重新连接 CarPlay 后仍存在。

使用已构建 OpenXPlay 的 `--record` 功能临时记录解密视频到板端内存目录，约 100 秒后自动移除录制参数并恢复正常服务，已核对恢复状态与服务 active。没有修改接收端二进制、固件或配对数据。媒体仅保存在本地忽略目录。
