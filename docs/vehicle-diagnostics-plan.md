# Lexus 实车诊断与菜单入口设计草案

状态：2026-10-30 计划核对。CarLife-only 探针尚未开发，尚未建立实验分支。运行基线为 `1aa023d`。原生菜单入口、返回投屏和统一软件音量已另行完成并验收，本草案保留诊断部分作为下一阶段。

## 目标与已确认的差异

1. 区分 CarLife 音频传输模式、逻辑音频通道、PCM 格式、车机焦点和车机本地音量，找出本车可用组合。
2. 在协议分发前保留收到的按键及未知控制消息，区分车机未发送、解析遗漏、映射遗漏与手机未响应。
3. 让盒子独立完成采集和结果标注，Mac 仅用于可选查看、导出和回放。
4. 复用已经完成的 CarLink 菜单、焦点导航与软件音量，不启动 HiCar/CarPlay 接收端。

源码调查发现：

- CarLink 的 `HU_INFO` 后发送 feature count=0 的请求；旧 CarProjection 列出 `FOCUS_UI`、`AUDIO_TRANSMISSION_MODE`、`MEDIA_SAMPLE_RATE`、`CONTENT_ENCRYPTION` 四项。应对照实际 HU 响应测试，不能直接将请求 USB 当作协商成功。
- CarLink 将 HU `AUDIO_TRANSMISSION_MODE=0/1` 分别解释为 USB/非 USB，并据此控制媒体输出。完整保留 feature 键和值，是声道诊断的前置步骤。
- 现有输入解析覆盖 Remote Touch 与若干 `0x68008` 按键，但还需要在过滤之前采集真实物理按键。音量、电话和切歌可能分别由车机本地系统、蓝牙或 CarLife 处理。
- HiCar 手机参考实现的 `BackToCarPackage` 不是普通第三方应用。点击路径调用 `notifyInCarUi`，再对 display service 请求状态 202；返回 HiCar 使用状态 203。实际线上 command 103 / action 202 与恢复 action 203 已核对、实现并通过台架验证。
- HiCar 桌面构造返回入口时，读取车机名称与品牌图标；有自定义名称/图标的实现逻辑。当前原生界面切换事件已连接菜单；系统返回入口名称/图标保持原样。

## 推荐的实车工具

在新分支 `codex/lexus-diagnostics` 实现可启停的诊断模式，复用现有 Rust manager、CarLife 与维护网页。先不再扩展 Android CarProjection；它保留为格式、行为和旧实车记录的参照。

车机端草图：

```text
CarLink · 实车诊断
音频测试 03：TTS / 48000 Hz / 单声道 / PCM16
协商模式：USB       播放状态：正在发送

[播放 3 秒]  [有声音]  [无声音]  [异常/失真]
[音量可调]  [音量不可调]         [下一组]

按键采集：[开始]  当前步骤：短按方向盘下一曲
收到：通道 / 消息号 / 原始字段 / 映射结果

[保存并退出]  [导出报告]
```

屏幕通过现有触控板焦点导航和按压操作；网页提供同样的测试编号和结果按钮。测试结果按编号即时保存，重启后仍可继续。

## 音频测试矩阵

“MEDIA/TTS/VR”是逻辑用途，不是左/右物理扬声器。先逐个测试逻辑通道，再测试单声道/立体声及左右输出。

阶段一固定低幅测试音，逐个检查 MEDIA、TTS、VR 的合法 INIT → DATA → STOP 序列。每组约三秒，结束后释放通道；任何时候可立即停止。

阶段二对可用通道测试 16/24/32/44.1/48 kHz 和单声道/立体声。实际 PCM 必须按选择重采样、混音或拆分，不能只更改 INIT 声明。优先复测旧 CarProjection 已记录的 TTS 单声道组合。

阶段三用同一格式比较当前协商、显式 USB 能力请求，以及播放前后焦点/模块状态；本 Lexus 在 CarLife 使用期间不支持连接原车蓝牙；若 HU 选择蓝牙，记录协商结果并测试明确 USB 请求，不把额外蓝牙配对列为测试前提。每次只改变一个条件。

每组记录：请求与响应、INIT 全字段、首末 DATA 时间、字节数、PCM 峰值/RMS、收到的 STOP/PAUSE/模块与焦点事件、是否可听、失真、旋钮/方向盘音量是否有效、是否打断或压低原车媒体。

音乐、导航和通话最终各自保存路由配置。TTS 可作为兼容路由；是否用于持续音乐，要同时检查音质、混音、焦点释放和音量行为。

## 按键与链路采集

- 在 CarLife 帧进入通道校验、白名单和映射之前记录 RX；发送端同样记录 TX。保存真实 channel、message ID、长度、序号、单调时间及解析结果。
- 控制消息保留原始 protobuf 与未知字段，媒体默认仅记录头部和计数；不持续录制音视频内容。原始控制记录保存在本机私有诊断目录，导出报告脱敏设备身份。
- 测试向导逐一提示：触控板、返回、主页、音量±、上一曲/下一曲、MODE、语音短按/长按、接听/挂断。每项测试按下、抬起、长按，建立动作与时间标记。
- 同时观察车机音源、媒体/通话状态及已有蓝牙控制事件。没有 CarLife 消息的按钮先按实际通路归类，不凭一次无响应判断为不支持。
- USB 状态、AOA、握手、源代次、音轨和进程事件共用时间线，便于区分 USB 断开、应用重启、播放器静音和接收端暂停。
- 异步有界日志队列与分卷，记录丢弃计数；采集工作不阻塞 USB/媒体线程。普通日志与增强控制采集分开配置。

## Mac 与无电脑使用

首选盒子开机自动记录，本地菜单标注结果，回家后导出。无需在车内维护编译环境或开着终端。

需要即时分析时，Mac 用 USB-C 网卡直连板上网口，可沿用固定管理网段，浏览器访问维护页，或使用系统自带 SSH/SCP。车机继续占用 Type-C，AX900 继续承载当前无线投屏；不为了诊断另外切换同一无线网卡的热点。

维护网页复用现有本地网段访问约束。Mac 接当前 CarLink AP 也是可选方式，但需先验证该协议/手机组合允许额外客户端；有线管理和离线记录作为常用路径。

## 音量控制

原生 CarPlay 的正常体验由车机调节音量，iPhone 侧物理音量键通常不控制 CarPlay。Apple 的系统集成资料也按音乐、导航、通话、铃声分别描述车机音量控制。

先核对本车是“媒体通道静音”“当前使用 TTS 导航音量”“焦点未释放”，还是所有 CarLife 输出确实都无法用旋钮调节。

盒子侧统一 PCM 音量已实现，菜单与网页共用设置，5% 步进、持久化及短渐变已验收，没有独立静音功能。各角色单独保存音量尚属可选扩展。iPhone 原生物理音量键协商仍作为单独实验。

AirPlay 的 volume 属性、能力声明及 SET_PARAMETER 可作为独立实验：确认手机实际发送音量命令后才接入 PCM 增益。普通 AirPlay 音量字段的存在，不能直接用作 CarPlay 路由可解锁的结论。

参考：[Apple 系统集成与音量管理](https://developer.apple.com/videos/play/wwdc2016/723/)、[TIDAL 官方 CarPlay 音量说明](https://support.tidal.com/hc/en-us/articles/18906946496017-CarPlay)、[AirPlay 协议字段](https://openairplay.github.io/airplay-spec/audio/rtsp_requests/get_info.html)。

## HiCar 菜单入口

推荐行为：点击原返回车机图标 → CarLink 菜单，HiCar 保持连接，音乐与导航音频继续；菜单提供“返回 HiCar”，显式选择其他协议时再完整交接资源。视频暂停或后台状态不再触发断线/自动抢回菜单画面。

功能入口已经完成并验收；独立名称/品牌图标定制留作可选外观项，不阻塞本轮 CarLife-only 探针。

## 开发顺序与验收

1. 被动采集与离线解析：保留未知字段，制造异常输入和日志压力，确保不改变正常会话。
2. 音频探测向导、按键标记和离线报告；新增 Mac 浏览器/导出说明。
3. 根据实车结果修正协商、路由及按键映射，保存本车兼容配置。
4. 完成真实 Lexus 握手、音频路由和实体按键验收，回归正常双协议运行。原生菜单入口与统一 PCM 音量已完成；iPhone 原生音量协商实验单独跟踪。

运行程序/固件改动仍由 GitHub Actions 编译，并完成完整固件校验、产物上传与台架回归后交付。实车测试在停车状态进行，每轮先固定一个变量，再测试组合场景。
